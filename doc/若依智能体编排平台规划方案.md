# 若依 + Spring AI 智能体编排平台规划方案（组件驱动版 V2）

> 目标：以 **Spring AI 组件关系** 为核心来设计平台，而不是先从传统业务菜单出发。
> 重点回答：`API -> Client -> RAG/MCP -> Agent -> Multi-Agent` 如何逐层组装、编排与治理。

---

## 1. 设计原则（先组件，后功能）

1. **组件可组合优先**：所有能力都抽象为可插拔组件（ModelClient、Retriever、ToolExecutor、Memory、Planner）。
2. **运行时可编排优先**：一个 Client 可在运行时动态挂载 Prompt、RAG、MCP 工具。
3. **分层编排优先**：
   - L1：单 Client 调用链编排
   - L2：单 Agent 内部节点编排
   - L3：Multi-Agent 协作编排（主管-专家-审校）
4. **治理内建优先**：trace、审计、权限、成本在每次调用链路强制注入。

---

## 2. Spring AI 组件视角：平台元素拆解

## 2.1 API 层（Platform API）

API 不是“业务接口集合”，而是“编排入口协议”：

- `Chat API`：一次对话请求，触发某个 Agent/Workflow。
- `Client Debug API`：只跑某个 Client 配置（便于调 Prompt/RAG 参数）。
- `Agent Run API`：执行单 Agent 编排图。
- `Multi-Agent Run API`：执行多 Agent 协作图。
- `Eval API`：对固定样本批量执行，输出质量指标。

**API 输入核心结构建议：**
- `appId` / `agentId` / `workflowId`
- `sessionId`
- `userInput`
- `context`（可选外部上下文）
- `runOptions`（模型、温度、topK、工具开关等动态覆盖参数）

## 2.2 Client 层（Spring AI Client Runtime）

可理解为“最小智能执行单元”，建议统一抽象为 `AiClientDefinition`：

- `modelSelector`：选模型（主模型/备模型）
- `promptTemplateRef`：提示词模板版本
- `advisors`：前后置增强器（上下文注入、输出校验）
- `retrieverRef`：检索器（可空）
- `toolsetRef`：可调用工具集（MCP/HTTP/内置）
- `memoryPolicy`：短期记忆策略
- `outputParser`：结构化输出解析器

### Client 的本质
一个 Client = `Prompt + Model + Advisors + (RAG?) + (Tools?) + Memory + Parser`

它负责完成“一次有边界的 AI 推理任务”，例如：
- 问答 Client
- SQL 生成 Client
- 工单总结 Client
- 风险审校 Client

## 2.3 MCP 层（Tool Protocol Layer）

MCP 在平台中扮演 **Tool Provider**：

- `McpServerRegistry`：注册多个 MCP Server
- `ToolCatalog`：同步工具元信息（name/desc/schema）
- `ToolPermissionGuard`：按租户/角色/Agent 控制可见和可调用
- `ToolExecutor`：统一执行 MCP 工具并返回标准结果

### MCP 与 Client 关系
- Client 不直接关心“工具在哪儿”，只关心“可用工具集合”。
- 工具由 `toolsetRef` 注入到 Client，执行时由 `ToolExecutor` 路由到具体 MCP Server。

## 2.4 RAG 层（Knowledge Retrieval Layer）

RAG 在平台中扮演 **Context Provider**：

- `KnowledgeIngestionPipeline`：文档解析、切片、向量化、入库
- `Retriever`：向量召回 / 混合召回
- `Reranker`（可选）：重排
- `CitationBuilder`：生成引用片段

### RAG 与 Client 关系
- Client 在推理前通过 `retrieverRef` 获取外部知识上下文。
- Retriever 输出被注入 PromptTemplate 变量（如 `{{knowledge}}`）。
- 最终回答强制带 citation，降低幻觉风险。

## 3. 关系模型：API、Client、MCP、RAG 如何组合

## 3.1 组合链路（单 Client）

`API Request` -> `ClientResolver` -> `PromptTemplate Render` -> `Retriever(Query)` -> `Assemble Context` -> `Model Call` -> `Tool Call(MCP)` -> `Post Advisor` -> `Response`

关键点：
- RAG 是“上下文增强环节”。
- MCP 是“动作执行环节”。
- Advisor 是“治理与加工环节”。

## 3.2 单 Agent 内的 Client 编排

一个 Agent 不等于一个 Client；**Agent = 多 Client 编排图**：

- `PlannerClient`：理解用户意图并拆分子任务
- `RetrieverClient`：构造检索策略并提取知识
- `ExecutorClient`：调用模型+工具执行任务
- `ReviewerClient`：质量审查与风险判断

编排模式：
- 串行：A -> B -> C
- 条件：A -> if(x) B else C
- 循环：A -> B -> A（带最大轮次）
- 并行：B || C -> D 汇聚

## 3.3 Multi-Agent 编排

多个 Agent 再构成更高层协作：

- `Coordinator Agent`（主管）负责路由与任务分解
- `Domain Agent`（专家）分别处理垂直子域
- `Judge Agent`（裁判）做一致性校验
- `Delivery Agent`（输出）合并并生成用户可读结果

典型模式：
1. **主管-专家模式**：Coordinator 分配给多个 Domain Agent 并汇总。
2. **辩论模式**：两个 Agent 给不同方案，Judge 做裁决。
3. **流水线模式**：Agent-A 产物作为 Agent-B 输入，逐步加工。

## 4. 编排模型设计（核心抽象）

## 4.1 三层抽象

1. **ClientDefinition**（原子能力）
2. **AgentDefinition**（Client 编排）
3. **AgentGraphDefinition**（Agent 编排）

## 4.2 节点类型建议

### Client 编排节点
- `prompt_node`
- `llm_node`
- `retriever_node`
- `tool_node`
- `condition_node`
- `review_node`
- `output_node`

### Agent 编排节点
- `agent_call_node`
- `agent_router_node`
- `agent_merge_node`
- `human_approval_node`
- `end_node`

## 4.3 状态机建议

- `draft` -> `published` -> `deprecated`
- 运行态：`created` -> `running` -> `waiting_tool` / `waiting_human` -> `success` / `failed`

## 5. 平台实体设计（按组件抽象）

## 5.1 Client 相关实体

1. `ai_client_def`：Client 定义（名称、用途、默认模型）
2. `ai_client_version`：版本化配置快照
3. `ai_client_prompt_binding`：绑定 Prompt 模板版本
4. `ai_client_retriever_binding`：绑定 RAG 检索器
5. `ai_client_toolset_binding`：绑定工具集
6. `ai_client_advisor_binding`：绑定前后置 Advisor

## 5.2 Agent 相关实体

1. `ai_agent_def`：Agent 定义
2. `ai_agent_version`：Agent 版本
3. `ai_agent_client_node`：Agent 内的 Client 节点
4. `ai_agent_client_edge`：Client 节点连线
5. `ai_agent_run`：Agent 执行实例
6. `ai_agent_node_run`：节点执行明细

## 5.3 Multi-Agent 相关实体

1. `ai_agent_graph_def`：多 Agent 协作图
2. `ai_agent_graph_version`：协作图版本
3. `ai_agent_graph_node`：节点（引用 agentId）
4. `ai_agent_graph_edge`：边与路由条件
5. `ai_agent_graph_run`：多 Agent 运行实例
6. `ai_agent_graph_node_run`：节点运行轨迹

## 5.4 MCP 与 RAG 实体

### MCP
- `ai_mcp_server`
- `ai_mcp_tool`
- `ai_mcp_tool_schema`
- `ai_mcp_tool_auth_policy`

### RAG
- `ai_kb`
- `ai_kb_doc`
- `ai_kb_chunk`

## 6. 库表关系重点（你最关心的组合关系）

1. **一个 AgentVersion 包含多个 ClientNode**
   - `ai_agent_client_node.agent_version_id -> ai_agent_version.id`
2. **每个 ClientNode 引用一个 ClientVersion**
   - `ai_agent_client_node.client_version_id -> ai_client_version.id`
3. **一个 ClientVersion 可绑定一个 Retriever + 多 Toolset**
   - `ai_client_retriever_binding.client_version_id`
   - `ai_client_toolset_binding.client_version_id`
4. **Multi-Agent Graph 的每个节点引用一个 AgentVersion**
   - `ai_agent_graph_node.agent_version_id -> ai_agent_version.id`
5. **运行日志可逐级回溯**
   - `graph_run` -> `agent_run` -> `client_node_run` -> `tool_call_log`

> 这样就实现了“Client 组合成 Agent，多个 Agent 再组合”的可追踪链路。

## 7. 运行时执行引擎建议

## 7.1 引擎分层

- `ClientEngine`：执行单 Client 调用链
- `AgentEngine`：调度 Agent 内 Client DAG
- `AgentGraphEngine`：调度多 Agent DAG

## 7.2 统一上下文对象

建议引入 `ExecutionContext`：
- `traceId` / `sessionId` / `tenantId` / `userId`
- `variables`（全局变量池）
- `artifacts`（中间产物）
- `toolBudget` / `tokenBudget`
- `securityLabels`

## 7.3 可观测与治理注入点

每层执行器都统一落：
- 输入摘要
- 输出摘要
- token 用量
- 耗时
- 失败重试与错误码
- 风险标记（敏感词、越权工具）

## 9. 分阶段落地（按编排能力递进）

### 阶段1：Client 运行时
- 完成模型调用 + Prompt 模板 + 基础 Advisor
- 做出可调试的 `Client Debug API`

### 阶段2：Client + RAG + MCP
- 给 Client 挂载 Retriever 与 Toolset
- 支持工具权限与调用审计

### 阶段3：Agent 编排
- 支持 Agent 内 Client DAG
- 支持条件、并行、失败重试

### 阶段4：Multi-Agent 编排
- 支持 AgentGraph 协作
- 支持主管路由与结果汇聚

### 阶段5：评测与优化
- 引入评测集和基线分
- 对 Prompt/RAG 参数/工具策略做 A/B

---

## 10. 给后续 AI Coding 的明确任务清单

1. 先生成三套核心实体与 DDL：`Client / Agent / AgentGraph`。
2. 再实现三层引擎骨架：`ClientEngine / AgentEngine / AgentGraphEngine`。
3. 先做最小可跑通链路：
   - 一个 Client（带 Prompt）
   - 一个 Agent（包含 2 个 Client 节点）
   - 一个 AgentGraph（串联 2 个 Agent）
4. 再补 RAG 与 MCP 插件化接入。
5. 最后补审计、成本、评测。

---

## 11. 验收标准（按你要求的编排模式）

1. 能创建一个 Client，并独立调试运行。
2. 能将多个 Client 编排成一个 Agent 并成功执行。
3. 能将多个 Agent 编排成一个 AgentGraph 并成功执行。
4. 能在执行过程中同时使用 RAG 检索和 MCP 工具。
5. 能完整追踪每次运行的 `graph -> agent -> client -> tool` 链路日志。
